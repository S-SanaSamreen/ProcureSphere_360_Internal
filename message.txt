PROJECT PURPOSE & NON-NEGOTIABLE RULES 1.1 Engineering Objective The purpose of this engagement is to verify sustained enterprise software engineering capability across requirements analysis, architecture, backend logic, database engineering, asynchronous processing, UI, security, testing, deployment, documentation and source-code governance. The application must operate as a real business system and not as a presentation-only prototype. 1.2 Mandatory Execution Rules • Minimum active engineering duration: 90 calendar days. • Final technical acceptance shall not be issued before the Day-90 review, even if development appears functionally complete earlier. • Formal technical reviews occur on Day 30, Day 60 and Day 90. • GitHub repository evidence is mandatory every 15 days, including repository URL, branch, immutable commit hash/tag, PR summary, CI/test status, staging URL and open defects. • Primary backend stack must remain Python/Django/DRF with PostgreSQL. Redis/Celery must be used for asynchronous or scheduled workloads where specified. • All workflow actions must persist to PostgreSQL and be protected by backend authorization. • Hardcoded mock workflows, fake success messages, dummy controls, copied boilerplate and frontend-only RBAC are rejection triggers. 1.3 Requirement Understanding Submission - Before Development REQUIRED ITEM WHAT VPD MUST SUBMIT Requirement Understanding Note Module-by-module interpretation, assumptions, exclusions and key risks. Clarification / Query Register Any ambiguity must be listed with requirement ID, question, impact and proposed assumption. Architecture Plan Application boundaries, data model approach, async tasks, API plan and deployment topology. Team Allocation Named or role-based assignment with accountable technical owners. Git Strategy Repository link, protected branches, PR approach, issue tracking and CI workflow. 90-Day Execution Plan 15-day delivery slices mapped to modules and review evidence. BUSINESS SCOPE & USER MODEL 3.1 Business Problem ProcureSphere 360 must replace disconnected email, spreadsheet and manual approval processes with a controlled source-topay workflow. Every requisition, sourcing event, bid, purchase order, receipt, invoice, contract and approval must be traceable to the responsible user, state, timestamp and supporting evidence. 3.2 Primary Roles ROLE PRIMARY ACCESS / RESPONSIBILITY Super Admin System configuration, all masters, roles, policies and audit visibility. Requester Create and track purchase requisitions for authorized departments/cost centers. Department Approver Review PR/business justification within approval limits. Procurement Executive Vendor, sourcing, negotiation, award and PO execution. Procurement Manager Approval oversight, policy exceptions, vendor governance and sourcing approval. Finance / AP Budget review, invoice validation, 3-way match exceptions and payment readiness. Stores / Receiver Goods/service receipt, inspection and quantity/quality acceptance. Legal / Contract Manager Contract review, versioning, obligation, renewal and termination controls. Compliance / Auditor Read-only audit, approvals, evidence and export access. Vendor User Restricted self-service onboarding, bid response, PO acknowledgement and selected documents. 3.3 Module Scope MODULE DETAILED REQUIREMENT Organization / Cost Center Legal entities, units, departments, locations, cost centers, fiscal periods and approval limits. Purchase Requisition Line items/services, justification, attachments, cost center, requested delivery, budget check and approval routing. Approval Policy Engine Rules by amount, department, cost center, transaction type and optional exception routing. Vendor Bid Portal Restricted bid submission, validation, attachments, amendment before close and sealed visibility. Evaluation & Award Commercial comparison, weighted technical scoring, negotiation notes, approval for award and decision audit. Purchase Order PO generation, taxes, delivery schedule, terms, versioning, change order/amendment and vendor acknowledgement. Receipt / Inspection GRN/service entry, partial receipt, quality acceptance/rejection, inspection notes and evidence. BUSINESS WORKFLOWS & RULES WORKFLOW MANDATORY STATES Vendor DRAFT -> SUBMITTED -> KYC REVIEW -> APPROVED / REJECTED -> ACTIVE -> ON HOLD / SUSPENDED Purchase Requisition DRAFT -> SUBMITTED -> MANAGER REVIEW -> BUDGET REVIEW -> APPROVED / REJECTED -> SOURCING / PO Sourcing Event DRAFT -> PUBLISHED -> BID WINDOW -> TECHNICAL REVIEW -> COMMERCIAL REVIEW -> AWARD APPROVAL -> AWARDED / CANCELLED Purchase Order DRAFT -> APPROVAL -> ISSUED -> ACKNOWLEDGED -> PARTIAL RECEIPT -> COMPLETED / CANCELLED Invoice RECEIVED -> VALIDATION -> 3-WAY MATCH -> EXCEPTION / APPROVAL -> READY FOR PAYMENT -> PAID / REJECTED Contract DRAFT -> LEGAL REVIEW -> BUSINESS APPROVAL -> ACTIVE -> RENEWAL DUE -> RENEWED / EXPIRED / TERMINATED 4.1 Critical Business Rules • Approval routing must be configurable and evaluated server-side from amount, department, cost center and policy rules. • Budget validation must distinguish available, reserved/committed and actual spend; the system must prevent silent overspend unless a documented exception route is used. • Vendor bids from competing suppliers must not be visible to other vendors. Reviewer visibility must respect the configured event stage. • PO amendments must preserve prior versions and require approval based on configured rules. • 3-way matching must compare PO, receipt/service entry and invoice, support amount/percentage tolerances and create explicit exception records. • Contract renewal/expiry notifications must be generated by scheduled Celery tasks and retain execution/audit evidence. • Audit records must capture actor, action, object, previous state, updated state, source IP/user agent where available and timestamp. 4.2 Edge Cases to Handle • Partial deliveries and multiple receipts against one PO. • Multiple invoices against one PO where business rules permit. • Rejected/returned goods and quantity correction without destroying history. • Vendor suspension while open sourcing or PO transactions exist. • Bid withdrawal/amendment before event close. • Approval delegate or approver unavailability. • Contract amendment that changes price/SLA/term while preserving prior version. • Duplicate invoice-number detection within vendor context. Before Day-90 acceptance. 7.3 Day-90 Acceptance Demonstration
Onboard a vendor with KYC documents, review it and approve it with a complete audit trail.
Create a purchase requisition above a configured threshold and prove multi-level approval routing and budget reservation.
Run an RFQ/RFP with at least three simulated vendor bids, perform technical/commercial evaluation and obtain award approval.
Generate a purchase order, amend it, record partial and final receipt and demonstrate preserved PO versions.
Submit an invoice, execute 3-way matching, trigger a tolerance exception, resolve it and move the invoice to payment-ready state.
